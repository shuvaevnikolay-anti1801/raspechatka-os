# DEV-155 — рабочий раздел «Чеки»

## Цель

Сделать раздел Windows POS «Чеки» полноценным рабочим журналом: кассир быстро находит нужный чек, видит полную расшифровку, безопасно печатает товарный чек/точную фискальную копию, запускает допустимый возврат и различает отложенные чеки по содержимому.

Baseline: `version-16` после DEV-154, merge `b5122230697f68b35fe41fd2aa08152387446c25`.

## Текущее состояние и причины проблем

- В `AppV2.tsx` экран называется «Чеки и возвраты» и использует `listSales()` + локальный `receiptQuery`, который реально ищет только номер чека и имя покупателя.
- `ReceiptFiltersBridge.tsx` содержит почти нужные фильтры, но подключён через portal к DOM и искусственно dispatch-ит input event. Он пишет фильтры в скрытое состояние preload, а текущий список `AppV2` вообще не вызывает `searchPointReceipts`. Поэтому фильтры не управляют таблицей.
- `ReceiptExplorer.tsx` содержит полезную разметку полной карточки чека, но не является частью рабочего экрана.
- Серверный `raspechatka/api/receipt_search.py` уже умеет point-scoped поиск по периоду/текущей смене, кассиру, сумме, способу оплаты и тексту (номер/клиент/телефон/товар).
- Локальный `receipt_mirror` хранит до 60 дней чеков точки с lines/payments для offline просмотра.
- `LocalReceiptTable` скрывает фискальную копию и блокирует возврат для `source='server'`.
- Товарный чек уже печатается через устойчивую `CommodityPrintQueue`.
- Критично: оба ATOL provider сейчас реализуют `reprintReceipt` как `printLastReceiptCopy`. Это печатает последний фискальный документ, а не гарантированно выбранный чек. Нельзя показывать такой результат как «копию выбранного чека».
- Текущий возврат безопасен для локальной продажи через TransactionEngine/Journal, но `saveReturn` опирается на локальные `sales/sale_items`. Server-only mirror не является локальной исходной продажей. Нельзя просто убрать `returnable:false`: это создаст риск двойного/некорректного возврата и сломает локальные FK/учёт.

## Архитектурные решения

### 1. Один настоящий ReceiptsPage

Создать отдельный renderer-компонент `ReceiptsPage` и перенести в него рабочий сценарий чеков. `AppV2` только переключает экран и передаёт нужный контекст/колбэки либо страница сама использует typed `PosApi`.

Удалить DOM-bridge подход:
- `ReceiptFiltersBridge` больше не монтируется в `main.tsx`;
- его логику перенести в страницу;
- старый `ReceiptExplorer` либо удалить после переноса полезной разметки, либо превратить в чистую детальную карточку без дублирующего отдельного поиска.

### 2. Поиск применяется явно

UI:
- строка: номер/фискальный номер, покупатель, телефон или товар;
- быстрые периоды: Текущая смена, Сегодня, Вчера, 7 дней, 30 дней, Период;
- для Период — дата с / дата по;
- Кассир;
- Оплата: Любая / Наличные / Безналичные;
- Сумма от / до;
- кнопки «Найти» и «Очистить»;
- Enter = «Найти»;
- «Очистить» возвращает default: Текущая смена + остальные поля пустые.

Не выполнять тяжёлый server search на каждую клавишу. Держать draft filters отдельно от applied filters.

### 3. Typed search API

Убрать скрытую mutable переменную `receiptSearchFilters` как контракт между UI и preload.

Добавить общий `ReceiptSearchFilters` в shared contracts и изменить API концептуально на:
`searchPointReceipts(query, filters)`.

UI оплаты — cash/noncash. На server boundary:
- cash => Cash;
- noncash => Card + QR (и другие non-cash, которые сервер нормализует как безнал);
- не заставлять кассира выбирать технический Card vs QR, если задача — найти безналичный чек.

Сервер остаётся строго scoped к business point POS-токена.

### 4. Online + offline

Online: использовать server receipt search как авторитетный поиск по истории точки.

Offline или server error: не ломать страницу. Фильтровать `listSales()`/receipt mirror локально по доступным полям и явно показывать, что это локальный кэш. Текущая смена, даты, сумма и cash/noncash должны работать локально. Если конкретное поле отсутствует в старом mirror snapshot, не выдумывать его.

### 5. Таблица

Колонки:
Чек | Дата/время | Кассир | Покупатель | Оплата | Сумма/статус | Действия.

В каждой строке всегда три понятных affordance:
- Товарный чек
- Копия чека
- Возврат

Отключённое действие остаётся видимым и имеет понятный `title`/reason.

Вся строка, кроме action buttons, кликабельна и открывает детали. Action button не должен одновременно открывать modal.

### 6. Детали чека

Modal/drawer:
- номер/фискальный номер;
- дата/время;
- кассир;
- покупатель + телефон, если есть;
- статус;
- способы оплаты и суммы;
- итог и скидки;
- товары: название, количество, цена, скидка, сумма строки, возвращённое количество;
- сведения об уже оформленных возвратах, если доступны.

Для результатов старше локального mirror добавить point-scoped server detail endpoint, если `getSale(id)` локально не может дать детали. Не создавать фальшивую локальную sale запись только ради просмотра/печати.

### 7. Товарный чек

Использовать существующий Windows printer flow/PrintProvider и существующую очередь для локальных/cached чеков.

Если найденный online чек не находится в локальном mirror, разрешить товарную печать только через безопасный snapshot деталей, достаточный для PrintProvider. Не вставлять такую продажу в локальный финансовый журнал как будто она была создана этой кассой.

### 8. Фискальная копия — safety invariant

`FiscalProvider.reprintReceipt(request)` должен означать «копия именно запрошенного фискального документа» или завершаться ошибкой. Запрещено печатать последний чек и подписывать его номером выбранного старого чека.

Для direct ATOL:
- подключаться только к уже выбранной ККТ и проверять её serial;
- реализовать capability-checked печать документа ФН по запрошенному fiscal document number через официальный Driver 10 report/read-FN mechanism;
- использовать late-bound Driver constants/properties, не копировать numeric constants;
- если текущий Driver/ККТ не предоставляет точную операцию — вернуть ясное «точная копия этого чека недоступна», без fallback на `printLastReceiptCopy`;
- операция копии не создаёт новую продажу/возврат.

Для legacy ATOL Web:
- если нельзя доказательно запросить конкретный документ, также fail closed;
- не использовать `printLastReceiptCopy` для произвольной исторической строки.

### 9. Возврат

Для локального чека этой POS:
- сохранить существующий ReturnModal + TransactionEngine + TransactionJournal;
- кнопка должна быть активной, если смена открыта, чек не возвращён полностью и `returnable!==false`;
- после возврата обновить страницу.

Для server-only/cross-POS чека:
- в DEV-155 НЕ снимать `returnable:false` простой UI-правкой;
- показывать кнопку, но disabled с объяснением: исходная продажа не сохранена как локальная операция этой кассы и безопасный межкассовый возврат требует центрального резервирования/idempotency;
- не обходить TransactionEngine и не создавать фиктивные local sale/sale_items;
- не выполнять bank/KKT refund без durable защиты от повторного возврата.

Это осознанное safety-ограничение текущей архитектуры, а не UI-баг.

### 10. Отложенные чеки

Карточка показывает:
- время;
- покупателя, если выбран;
- сумму;
- количество позиций;
- до 3–4 строк товаров (название + количество), затем «+ ещё N»;
- кнопку «Продолжить».

Добавить в `HeldReceipt` optional `totalMinor` и сохранять его в момент откладывания. Старые payload без поля остаются читаемыми; fallback total считать из сохранённых lines/discount данных. Отдельная SQL migration не нужна, payload уже JSON.

## Acceptance

- Заголовок страницы только «Чеки».
- Фильтры реально определяют результаты; есть «Найти», Enter и «Очистить».
- Online поиск использует сервер; offline остаётся полезный локальный поиск.
- В таблице есть кассир и три action buttons.
- Row click показывает полную расшифровку.
- Товарный чек печатается существующим printer flow.
- Фискальная копия никогда не печатает другой «последний» чек вместо выбранного.
- Локальный допустимый возврат запускается; fully-returned/unsafe server-only корректно disabled с причиной.
- Отложенные чеки показывают клиента, сумму и компактный состав.
- Старые HeldReceipt payload совместимы.
- Нет новых зависимостей и нет широкого рефакторинга кассы.
