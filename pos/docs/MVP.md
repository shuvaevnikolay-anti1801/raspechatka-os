# Границы первой кассы

## Цель

Сначала получить надёжную кассу уровня основной ежедневной работы, затем добавлять функции рабочего места менеджера. Интерфейс ориентируется на понятные сценарии кассы МойСклад, но код и визуальная система принадлежат Распечатке.

## Этапы

| Этап | Результат | Статус |
|---|---|---|
| 0. Каркас | Окно Windows, локальная база, тестовый каталог, чек, оплата, очередь синхронизации | В этой ветке |
| 1. Продажа | Поиск/сканер, скидки, клиент, наличные/карта/QR/смешанная оплата, отложенный чек | Готово в прототипе |
| 2. Смена | Открытие/закрытие, внесение/изъятие, расчёт ожидаемой наличности | Готово в прототипе |
| 3. Операции | Полные/частичные возвраты по исходному чеку, история операций | Готово в прототипе |
| 4. Покупатели и склад | Клиент из OS, его скидка и история покупок; остатки и движения по точке | Готово в прототипе |
| 5. Печать | Товарный чек Windows; интерфейс повторной фискальной печати | Готово, ККТ пока в тестовом режиме |
| 6. Оборудование | АТОЛ 1Ф и эквайринг | После настройки драйвера ККТ и выбора терминала |
| 7. Заказы | Предоплата, выдача и статусы производства | Отложено до появления модели заказов в OS |

## Архитектурные правила

1. **Offline-first.** Продажа сначала надёжно записывается локально, затем отправляется на сервер.
2. **Деньги — целые копейки.** В расчётах не используются числа с плавающей точкой.
3. **Идемпотентность.** Повторная отправка одного события не создаёт дубль продажи.
4. **Оборудование за адаптерами.** Бизнес-логика не зависит напрямую от конкретной модели ККТ или терминала.
5. **Минимальный IPC.** Интерфейс React не получает прямой доступ к Node.js, файлам и драйверам.
6. **Сервер — источник общих справочников.** Локальная база хранит рабочую копию каталога и несинхронизированные операции.

## Разделение ответственности

| Часть | За что отвечает |
|---|---|
| React | Быстрый интерфейс кассира и менеджера |
| Electron main | Безопасная бизнес-логика, база, драйверы, синхронизация |
| SQLite | Продажи и рабочие данные на конкретной кассе |
| Frappe | Централизованные товары, точки, сотрудники, права, аналитика |
| Провайдеры | АТОЛ, эквайринг, печать, сканер |

## Что намеренно не считается готовым

- тестовый чек не является фискальным;
- «оплата картой» не обращается к банковскому терминалу;
- каталог синхронизируется с Frappe после настройки API, но без настройки остаётся демонстрационным;
- заказы и предоплаты намеренно не реализуются до появления модели заказов в OS;
- повторная фискальная печать использует тестовый адаптер, товарный чек — системную печать Windows;
- продажи и возвраты попадают в журнал событий OS, историю покупок клиента и складские движения.
