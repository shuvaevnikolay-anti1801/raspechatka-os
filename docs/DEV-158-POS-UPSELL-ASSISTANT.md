# DEV-158 — Помощник дополнительных продаж POS

## Цель

Добавить сетевой помощник дополнительных продаж: администратор Raspechatka OS настраивает связи «основной товар/услуга → что предложить», Windows POS получает правила при штатной синхронизации, хранит их локально и во время продажи показывает кассиру одно ненавязчивое предложение с готовой фразой и кнопкой добавления позиции в текущий чек.

Функция должна работать offline-first и не менять бизнес-логику продажи, расчётов, оплаты, фискализации, возврата или складских движений.

## Пользовательский сценарий

1. В Web OS пользователь с правом редактирования «Продажи → Подключение кассы» открывает новый блок «Дополнительные продажи» под «Общие настройки продаж».
2. Он выбирает основной продаваемый Catalog Item и добавляет один или несколько кандидатов для допродажи из существующего каталога.
3. Для каждого кандидата можно задать готовую фразу кассиру. Если фраза пустая, используется fallback «Предложите покупателю: <наименование>».
4. Правила сетевые и одинаковы для всех касс. Точки в настройке не выбираются.
5. POS получает правила вместе с обычным bootstrap и продолжает использовать последний успешный локальный snapshot без интернета.
6. Когда в текущий чек добавлен товар/услуга с активным правилом, POS показывает в правой области чека одну компактную зелёную карточку: заголовок «ПРЕДЛОЖИТЕ ПОКУПАТЕЛЮ», готовую фразу, наименование и цену рекомендуемой позиции, кнопку «+ Добавить» и ненавязчивое закрытие.
7. Кнопка «+ Добавить» вызывает тот же существующий путь добавления Product в cart, что и карточка каталога.
8. После принятия или отказа новое предложение в этой продаже не показывается до очистки/завершения текущего чека.

## Модель данных

Создать отдельную конфигурационную модель, не расширяя одиночный POS Sales Settings структурированными списками.

### POS Upsell Rule

- trigger_item — Link → Catalog Item, обязательный, уникальный.
- enabled — Check.
- candidates — Table → POS Upsell Candidate.
- системные поля Frappe / track_changes.

### POS Upsell Candidate

- item — Link → Catalog Item, обязательный.
- cashier_phrase — Small Text, необязательный.
- порядок child row (idx) задаёт порядок ротации.

Инварианты:
- один trigger_item — одно правило;
- target не равен trigger;
- одинаковый target нельзя повторить внутри одного правила;
- включённое правило содержит минимум одного кандидата;
- в настройке используются существующие активные продаваемые Catalog Item; parent Product с активными Variant не должен становиться POS SKU;
- архивирование/исчезновение позиции не должно ломать POS: bootstrap просто не передаёт неактуальную комбинацию.

## Доступ и API Web OS

Не создавать новую страницу или новый access area. Использовать существующий page.sales.integration.

Новые/изменённые whitelisted endpoints обязаны иметь @access_contract.

Предпочтительный контракт:
- read config/catalog options: page.sales.integration, action read, scope network;
- save config: page.sales.integration, action write, scope network, дополнительно требовать global/network scope как существующий save_pos_sales_settings.

Frontend hiding не является защитой.

## Bootstrap и point scope

Расширить существующий raspechatka.api.pos_v2.get_bootstrap, не добавляя отдельный POS endpoint.

Алгоритм:
1. Сначала получить обычный point-specific products.
2. Построить множество фактически доступных POS product IDs для этой точки.
3. В upsellRules включать только правила, где trigger присутствует в этом наборе.
4. В candidates включать только target, который также присутствует в point product IDs.
5. Если после фильтрации candidates пусты — правило не передавать.

Таким образом POS token не получает сведения о каталоге вне своей точки.

## Локальное хранение Windows POS

Не создавать отдельную SQLite-таблицу без необходимости.

- Добавить upsellRules в shared bootstrap/BootState contracts.
- Успешный sync сохраняет snapshot правил вместе с существующим bootstrap в app_state.
- buildBootState() восстанавливает правила из последнего сохранённого snapshot.
- При недоступной OS POS использует последнее успешное состояние.
- Для round-robin использовать app_state cursor на rule/trigger; новой таблицы не требуется.

## Выбор рекомендации

POS никогда не показывает несколько вариантов одновременно.

Для каждого trigger candidates имеют стабильный порядок. Локально используется круговая ротация:
1. взять сохранённый cursor;
2. начиная с него найти первый допустимый target;
3. при необходимости пройти список с wrap-around;
4. после выбора сохранить следующий cursor, чтобы следующий чек получил следующий вариант.

Не использовать случайный Math.random() как источник поведения UI.

Candidate считается допустимым, если:
- target есть в локальном активном списке products;
- target ещё не находится в текущем cart;
- если trackInventory=true и остаток <= 0, а allowNegativeStock=false, target пропускается.

Состояние текущей продажи:
- пока предложение не выбрано — eligible;
- после появления одной рекомендации она не должна самопроизвольно меняться из-за изменения количества;
- принятие, отказ или удаление trigger после показа завершает upsell для текущего чека;
- очистка/успешное завершение чека начинает новый cycle.

## POS UX

Карточка не modal, не перекрывает каталог и не мешает обычному добавлению позиций.

Расположение: правая область текущего чека, после списка позиций и до нижних скидок/действий.

Визуально:
- светло-зелёный/зелёный акцент;
- компактная высота;
- заголовок «ПРЕДЛОЖИТЕ ПОКУПАТЕЛЮ»;
- phrase;
- target item + текущая локальная POS цена;
- primary action «+ Добавить»;
- secondary dismiss.

Не добавлять отдельный sale path, price override, discount logic или transaction semantics для рекомендованной позиции.

## Сопутствующий UX cleanup области чека

В этот DEV входят утверждённые изменения правой панели:

1. Убрать отдельный блок/строку «Итого» из области чека. Итог остаётся на кнопке «К оплате · <сумма>».
2. Убрать постоянный текст «ККТ и оборудование проверяются перед каждой оплатой». Сами проверки оборудования не менять.
3. При наличии скидки:
   - строку «Без скидок» показывать без зачёркивания;
   - ниже показывать «Скидка составила» и общую сумму скидки;
   - не добавлять второй итог.
4. В Windows POS не показывать лишние ,00 для целых рублей.
   - внутреннее хранение и расчёты остаются в minor units;
   - не менять payload, оплату, фискализацию или округление;
   - если неожиданно встречается сумма с ненулевыми копейками, UI не должен молча округлять её до рублей: дробная часть должна остаться видимой.

Рекомендуется вынести renderer-only money formatter в маленький общий helper и использовать его в активных POS-компонентах вместо дублирующихся Intl.NumberFormat.

## Не входит

- рекомендации по категориям/группам;
- условия по сумме чека, времени, клиентскому сегменту;
- AI/ML-рекомендации;
- несколько одновременно показанных предложений;
- цепочка «после допродажи предложить ещё»;
- изменение TransactionEngine, payment/fiscal providers, ATOL/INPAS;
- изменение расчёта цен, скидок, ассортимента, склада;
- отдельная аналитика конверсии upsell (может быть следующим DEV).

## Проверки

Focused tests должны покрывать:
- backend validation правил и access contract;
- point-scoped bootstrap filtering;
- сохранение upsellRules в offline bootstrap;
- deterministic round-robin и пропуск недоступных target;
- отсутствие второго предложения после accept/dismiss;
- «+ Добавить» добавляет обычный Product в cart;
- receipt UX: нет второго итога, нет training text, скидка показана новой формой;
- money formatter: целые рубли без ,00, ненулевые копейки не теряются.

Полный CI / frontend build / POS typecheck+tests+build / Windows package — один раз в конце DEV перед единственным PR.
